## מסמך מחקר ואפיון מוצר, תהליכים, מסמכים וארכיטקטורה — v0.1
**תאריך:** 12.10.2026 | **סטטוס:** אפיון להצעת POC, לא תיאור מערכת בנקאית קיימת | **קהל יעד:** מנהלת מוצר/פרויקט, JEEN Engineering, צוות דמו, גורמי משכנתאות ו־IT של הבנק

> **המסר הניהולי:** לא בונים אפליקציית משכנתאות חדשה. מוסיפים לטפחות טאצ׳ שכבת AI שיודעת מה עלה, מה חסר, מה סותר, מה נכון לבקש עכשיו ומה ראוי להעביר לבנקאי — עם ראיות ובקרה. צ׳אט ודיבור הם שני ערוצים לאותו מנוע תהליכי.

## 1. תקציר החלטות

**המצב הקיים שאומת:** טפחות טאצ׳ היא אפליקציית משכנתאות אמיתית של מזרחי־טפחות המאפשרת הגשת בקשה, עדכון על אישור עקרוני, סטטוס ושלבים, העלאת/הורדת מסמכים, התכתבות ותיאום פגישה עם מומחה משכנתאות, מחשבון וכלים נוספים [S01–S03]. קיימת גם סביבת טפחות טאצ׳ ליועצי משכנתאות [S04]. הבנק מדגיש את הליווי האנושי.

**הזדמנות מוצעת:** AI להשלמת תיקים מבוססי מסמכים (Document Readiness): זיהוי סוג מסמך, חילוץ שדות ותקופות, בדיקת שלמות על פי דרישות התיק, הצלבת מקורות, בקשת השלמה ממוקדת, תיעוד ראיות ומסירת תקציר לבנקאי. תיתכן חפיפה למערכות פנימיות קיימות שאינן חשופות לציבור; יש לבדוק ב־Discovery.

**Vertical slice ראשון:** זוג שכירים הרוכש דירה יד שנייה, אחרי אישור עקרוני; חסר תלוש שכר אחד בגלל כפילות. הסוכן מזהה, מסביר, מבקש השלמה, בודק שוב; פער נוסף מסומן לבנקאי בלי להסיק מסקנת אשראי.

**גבול סמכות:** JEEN אינה מאשרת אשראי, אינה משנה תנאי משכנתא, אינה מחליפה בדיקת בנקאי, אינה מעניקה פרשנות סופית לבטוחות משפטיות, ואינה משנה סטטוס בנקאי רשמי ללא פעולה מאושרת במערכת הבנק.

**תוצרת קלוד המבוקשת:** Discovery עצמאי של קוד/סביבות/רכיבי JEEN הקיימים, מפת פערים מאומתת, ארכיטקטורה מומלצת, Implementation Plan ו־Demo Plan. **לא לבצע Implement לפני אישור התוכנית.**

**הצילומים שסופקו בשיחה:** הם ממחישים מסך בקשה פעילה, התקדמות בשלבים, כרטיס בנקאי, פירוט בקשה, אזור מסמכים, העלאת פריטים חסרים והתראות. בתמונות חלק מהתאריכים הם מ־2021–2022; לכן אלה **ראיות UI להמחשה**, לא אימות שכך נראית גרסת האפליקציה הנוכחית ב־2026. אין להסתמך על “2/5” כמודל סטטוסים מחייב.

### 2.1 נקודות כניסה אפשריות בתוך האפליקציה

1. **אזור ״מסמכים״:** פעולה משנית: ״בדיקה חכמה למסמכים שהעליתי״; תוצאות לכל מסמך והנחיית השלמה.
2. **כרטיס התקדמות הבקשה:** שאלה ״מה חסר כדי שאוכל להתקדם?״ — תשובה מסטטוס התיק ומה־readiness הפנימי.
3. **אזור שיחה עם מומחה:** ״לשאול את עוזר המשכנתא״ לצד אפשרות ברורה לעבור לבנקאי.
4. **כפתור דיבור:** ״לדבר עם העוזר״ — JEEN Talk כאופציית ערוץ, לא תנאי לעבודה במסלול הטקסט.
5. **תצוגת בנקאי נפרדת:** סיכום ראיות, חוסרים, אי־התאמות ו־Next Action, בלי להעתיק את UI הלקוח למערכת הבנקאי.

**UX:** לשמור על הניווט הקיים (ראשי/מסמכים/שלבים/פגישות/כלים כפי שמופיע בצילומים), הכתום והכחול־אפור; להוסיף רכיב מעטפת קטן עם תווית ״הדגמת יכולת AI מוצעת״. לא לבנות מסכי בנק חדשים כאילו הם חלק ממערכות מזרחי.

**סיווג ״ראינו מסמך״ ≠ ״המסמך אושר״.** חובה לתחזק לכל פריט את הסטטוסים: not_required / required_missing / uploaded_unreadable / extracted / needs_customer_action / needs_banker_review / accepted_by_bank / expired. רק גורם מורשה יכול לקבוע `accepted_by_bank`.

## 5. תרחיש הדמו המומלץ — אחד, עקבי, עם ראיות

**Personas סינתטיים:** עידו ונועה, שניהם שכירים, רכישת דירה יד שנייה; לא להשתמש במקביל במסמכי עצמאי/אישור רו״ח.

**תאריך סימולציה:** 12.10.2026; שלושת חודשי השכר לצורך הדגמה הם יולי, אוגוסט וספטמבר 2026 (בכפוף לכך שלקוח באמת נדרש להמציא חודשים אלה לפי מועד תשלום השכר). **רצף אירועים:**

1. **בקשה ידועה:** האישור העקרוני כבר התקבל; רשימת דרישות מסמכי ההכנסה מוצגת מתוך Mock Bank Case API. אין להציג ״אישור סופי״.
2. **העלאה:** לתיק עידו צורפו יולי, אוגוסט ו**אוגוסט פעם נוספת**; חסר ספטמבר. לנועה צורפו המסמכים הנדרשים כראוי.
3. **Document AI:** VisionTrace או Adapter חילוץ מתעד לכל תלוש את שם העובד, החודש, השנה, סכום השכר, מקור הדף ומיקום הראיה. אם אינו זמין — fallback engine מדומה ומסומן במפורש.
4. **כללים דטרמיניסטיים:** `REQUIRED_PERIOD_MISSING(2026-09, עידו)` ו־`DUPLICATE_PERIOD(2026-08, עידו)`; לא לסמן ״הכנסה לא תקינה״ רק מכפילות.
5. **שיחה/דיבור:** העוזר מסביר: ״קיבלנו שני תלושי אוגוסט. בשביל להשלים את מסמכי ההכנסה צריך את תלוש ספטמבר של עידו״. הלקוח יכול להעלות קובץ או לענות בקול.
6. **תיקון:** העלאת ספטמבר, בדיקה חוזרת **רק של הפריטים הנוגעים לשינוי**, עדכון readiness הפנימי.
7. **חריג נפרד (אופציונלי):** נתון הכנסה בבקשה שונה מנתון בתלוש של נועה; הלקוחה נותנת הסבר, אבל המערכת מסמנת `NEEDS_BANKER_REVIEW` עד לבדיקת ראיה/אישור בנקאי. לא ״פותרים״ פער בהצהרה בלבד.
8. **סיכום לבנקאי:** טבלה עם דרישה, מצב, ממצא, confidence, ראיה (document/page/bbox), מי התבקש לפעול, מה עדיין פתוח. ה־AI רשאי לומר ״הושלמו מסמכי השכר המבוקשים״ אך לא ״כל תיק המשכנתא הושלם״.

**הדמו חייב להראות שלוש סצנות קצרות:** (א) לפני העלאה/פער, (ב) השלמה, (ג) Case Review לבנקאי. ייצוא JSON/דוח הוא בונוס, לא לב הערך. התהליך משאיר ״המשך טיפול בבטוחות/שמאות״ כשלב בנקאי אחר, בלי לקבוע שנשאר רק זה.

## 7. חוויית צ׳אט וקול — JEEN Talk

**חוויה אחת:** צ׳אט וטוק הם `interaction_channel` שונים ל־`case_id` ו־`conversation_id` משותפים, ללא שני מקורות אמת. הלקוח מתחיל בשאלה ״מה חסר?״ בטקסט, יכול ללחוץ ״דבר איתי״, לשאול בקול ולחזור לטקסט; סיכום, פעולות וכללים נשארים אחידים.

**תסריט Voice קצר לדמו:** לקוח: ״מה נשאר כדי לסיים את המסמכים?״ → הסוכן: ״חסר תלוש ספטמבר של עידו; קיבלנו אוגוסט פעמיים״ → לקוח: ״אני אעלה אותו עכשיו״ → הסוכן: ״מעולה, כשתעלה אבדוק מחדש. אפשר גם לשלוח למומחה המשכנתאות שאלה״.

**עקרונות Voice:** הסכמה לביצוע עיבוד אודיו ותמלול לפי מדיניות הבנק; הצגת תמליל לתיקון טעויות זיהוי דיבור; נתונים אישיים בטקסט וקול באותה בקרת הרשאות; אין הקלטה/שמירה אוטומטית בלא מדיניות ואישור; לא להקריא בקול פרטים מזהים רגישים ללא אימות; escalation לאדם; כפתור השתקה/סיום; transcript provenance (speech vs typed). JEEN Talk הוא **Integration Slot**: על קלוד לבדוק בפועל APIs, latency, streaming, ASR/TTS, session hooks והרשאות. אין להציג את כולן כיכולות שכבר חוברו.

## 8. ארכיטקטורת יעד — JEEN Ecosystem + MCP

```
טפחות טאצ׳ (host app) / Demo shell
       ├── Chat UI ──────────────┐
       ├── JEEN Talk (voice) ────┤  same case_id + conversation_id
       └── File upload UI ───────┘
                     ↓
            JEEN Orchestrator / Agent Factory
         ├── Intent + dialogue state
         ├── Document Readiness Agent
         ├── Completion / Follow-up Agent
         ├── Banker Case Summary Agent
         └── Governance policies + evaluation + FinOps
                     ↓
             Tools / Workflows Gateway
         ├── VisionTrace adapter (verify capabilities)
         ├── PDF native text extraction + OCR fallback
         ├── Requirements / Rule Engine
         ├── Document store + Evidence Service
         ├── Case state + Task workflow
         └── MCP Client / Bank API Gateway (mock first)
                     ↓
           Authoritative Bank Systems (unknown)
         case status | document metadata | banker inbox
```

**Critical distinction:** השם VisionTrace מזוהה עם כלי בדיקת שרטוטים הנדסיים בפרויקט JEEN. **לא אומת שהמנוע הנוכחי מתאים מחוץ לקופסה לחילוץ מסמכי משכנתא.** על Claude לבדוק יכולות, רישוי, פורמטים, ראיות, התאמת מודל ויכולת Custom Schema. אם הפער גדול, נכון לתכנן `DocumentExtractionProvider` ולבחור מימוש אחר ל־POC במקום לכופף מנוע שאינו מתאים. רכיב VisionTrace נשאר slot ברור.

**MCP הוא אמצעי אינטגרציה אפשרי, לא הוכחה שקיימים MCP Servers של מזרחי.** גישה מאובטחת דרך שכבת Adapter עם allowlist, scopes, אימות לקוח, audit, timeout, retries, idempotency והפרדה בין קריאה לכתיבה; לא לאפשר ל־LLM גישה חופשית למערכות בנק.

### 8.1 חוזי API/MCP מוצעים בלבד

| Tool | כיוון | מטרה | מדיניות |
|---|---|---|---|
| `get_mortgage_case(case_id)` | READ | פרטי בקשה וסטטוס בנקאי | case.read, scoped borrower |
| `list_case_requirements(case_id)` | READ | דרישות הבנק לתיק | read-only, bank authoritative |
| `list_case_documents(case_id)` | READ | metadata ומזהי מסמכים | read-only; signed retrieval |
| `submit_document_for_review(case_id, file_ref, consent)` | WRITE | שליחת מסמך בתהליך מאושר | customer confirmation + scan + auth |
| `get_banker_review_queue(case_id)` | READ | מצבי טיפול אנושי | banker-only, allowlisted |
| `create_banker_followup_draft(case_id, finding_refs)` | WRITE DRAFT | טיוטת העברה לבדיקה | אין שליחה בלא אישור מפורש |
| `get_case_stage_dictionary()` | READ | מיפוי שלבי בנק מוצהר | מקור האמת בבנק |

**API envelope מומלץ:** `request_id`, `case_id`, `actor_id`, `role`, `scopes`, `channel`, `consent_ref`, `idempotency_key`, `trace_id`, `policy_version`. תוצאות כוללות `source_system`, `retrieved_at`, `schema_version`, `data_freshness`, `redaction_flags`.

### 8.2 סכמת ראיות מינימלית

```
DocumentEvidence {
  case_id, document_id, borrower_id, document_type,
  file_checksum, extraction_provider, model_version,
  field_name, value, normalized_value, confidence,
  page_number, bbox_or_text_span, source_timestamp,
  extraction_status, reviewer_action
}
Finding {
  finding_id, reason_code, severity, requirement_id,
  borrower_id, evidence_refs[], policy_version,
  review_state, action_owner, customer_message,
  created_at, resolved_at
}
```

**עיקרון:** לא כל ממצא הוא ״שגיאה״. לדוגמה פער הכנסה יכול להיות מוסבר בבונוס/תוספת/החזר, אך בלי ראיות תומכות יש לסווג אותו `NEEDS_BANKER_REVIEW` ולא `RESOLVED`.

### 8.3 שתי מכונות מצב נפרדות

- **Bank case stage** — רשמי: נוצר/נבחן/אושר עקרונית/ממתין למסמכים/בדיקת בנקאי וכו׳ **בהתאם למיפוי שנקבל מהבנק**. לא להמציא ״חמישה שלבים״ מחייבים.
- **AI document-readiness state** — מוצע: NOT_CHECKED → CHECKING → ACTION_REQUIRED → RECHECKING → READY_FOR_HUMAN_REVIEW / HUMAN_REVIEW_REQUIRED. ה־AI יכול לעדכן **רק** את state הפנימי שלו ב־POC. כניסה לסטטוס רשמי דורשת API והרשאה מוסדרים.

## 9. QA, הערכה ואבטחת מידע

**בדיקות קבלה:**
- בלי hallucinations: אין ״התקבל אישור סופי״, אין ציון סכום מאושר/ריבית שלא חזר ממקור מאומת.
- Confidence מתועד לכל חילוץ; ערכי confidence אינם מחליפים QA, ויש להגדיר סף במו״מ עם bank SME.
- Proof: לכל reason_code הקשור למסמך אפשר לפתוח ראיה ספציפית; אין מקור? מדווחים `evidence_unavailable`.
- Negative cases: תלוש כפול, חודש חסר, עמוד חסר בחוזה, PDF ללא טקסט, קובץ פגום, שם לווה שגוי, מסמך מתיק אחר, שינוי סטטוס סותר, דיבור לא מובן, prompt injection מתוך PDF.
- Privacy: נתונים סינתטיים בלבד עד אישור בנק; RBAC/ABAC, no cross-case leakage, הצפנה, retention, masking, audit ונוהל מחיקה.
- Security: prompt injection resilience, scanning, MIME sniffing, size limits, signed URLs, no arbitrary tool execution, tool-level approvals.
- Voice: שיבוש הקלדה/ASR, חזרה מטוק לצ׳אט, אימות זהות לפני גילוי פרטים, handoff אנושי.
- Quality Gate מומלץ לדמו: **100% של הממצאים המודגמים משויכים לראיה, 0 החלטות אשראי אוטומטיות, 0 קריאות ל־Bank API אמיתי ללא הרשאה, וכל שלושת שלבי הסיפור ניתנים לשחזור.** אלו קריטריונים שהצוות מציע, לא מדדי ביצועים מוכחים.

**KPI עסקיים לבנק שצריך לקבל לו baseline:** דקות טיפול אנושיות לתיק; מספר סבבי השלמה; שיעור מסמכים שחוזרים בגלל שגיאה; זמן מהעלאה ועד תיק מוכן לבדיקה; שיעור False Positive; שביעות רצון לקוח/בנקאי; שיעור תיקים שמגיעים לבחינה מלאה (מדד ארוך טווח). לא להבטיח אחוזי חיסכון לפני מדידה.
